# 模式对照的预算梯度与重复实验

本文保留 V1 历史实验及其原始证据。2026-10-30 已放弃未提交的 Repair V2 产品改动，
恢复已提交基线，研究转向上下文管理；本文与论文继续在原文件维护。
下文模型运行命令是历史协议，运行脚本已从开发工作区清理；复现须使用对应源码归档。
已有原始成绩不能续填为新上下文策略结果；新指标可在本报告中增量分析并明确数据来源。

本轮继 [2,048 输出额度的初步实验](mode-comparison.md)之后，恢复项目默认的单次
8,192 token 输出额度，比较累计任务预算对真实修复结果的影响。

## 预先固定的条件

- 任务：固定 python-dotenv v1.1.1 上的 8 个人工缺陷，沿用原始验收和额外测试。
- 模式：真实公开 SDK 的 ReAct、Plan、Team、Repair / verified。
- 累计预算：60,000、120,000、240,000 token；每个任务、模式、预算重复 3 次，共 288 次。
- 模型：加载当前项目配置，供应商与模型标识保存在原始报告；temperature=0。
- 单次最大输出：8,192 token，包含本次模型返回的 reasoning 额度。
- 兜底限制：最多 64 次模型请求、900 秒，Repair 最多 3 轮尝试。
- 四组统一使用受限文件工具和 Docker 命令环境；关闭 Memory、MCP 和自定义 Prompt 文件。
- 全部运行用固定随机种子 20261029 打乱，最多同时运行 4 个相互隔离的任务。
- 保持产品代码基线一致；归档实际实现源码和 fixture，逐个文件记录 SHA256。

总 token 在下次请求前依据已返回 usage 检查，仍是软上限；并发角色和最后一次请求可能使
实际用量超过阈值。模型调用次数涵盖所有角色。不同运行的客户端、上下文、预算与工作副本均独立。
模型调用内部并发保持各模式本身的行为。

这是统一工具环境下的编排对照，不等于普通 CLI 的完整默认宿主工具体验。四个独立任务并发，
机器、供应商负载与缓存影响耗时，耗时仅作描述；主要指标是额外测试通过数、正常结束且通过数
及实际累计 token。三次重复仍然是小样本，不进行未经支持的显著性或普遍能力宣称。

## 运行与续跑

```bash
uv run python -m eval.run_budget_grid \
  --budgets 60000 120000 240000 --repeats 3 \
  --output-tokens 8192 --calls 64 --timeout 900 --concurrency 4 \
  --out eval/evidence/budget-grid-20261029

# 原进程已退出后才续跑；实现或条件不同会被拒绝。
uv run python -m eval.run_budget_grid \
  --out eval/evidence/budget-grid-20261029 --resume
```

原始源码先验证干净版本通过两套测试、每个缺陷都产生真实失败，再开始模型调用。
每次结果立即落盘。若完整结果已保存而总表尚未更新，续跑会从结果文件恢复，避免重复调用。
运行目录存在但尚无完整结果的任务会报错，需要检查该次调用记录后归档不完整任务，才能重试；
不会把它当作已经完成。不要同时启动两个进程写入同一个实验目录。

归档目录包含：

- `grid.json`：完整排程、协议、逐次简表、按预算和模式汇总，以及每个重复轮次的统计。
- `runs/<预算>/r<轮次>/<任务>/<模式>/result.json`：完整结果和外部测试输出。
- 同目录 `events.jsonl`：模型事件、工具结果及普通模式编排事件。
- `repair-runs/`：Repair 自身的候选补丁、报告和角色事件。
- `implementation.zip`：运行开始前保存的实际实现、内置 Prompt/Skill 和 fixture。

通过标准沿用初步实验：评测器对最终可取得的候选重新运行原始 9 项验收，再加入模型运行时
不可见的 4 项检查。普通模式即使中断也评测最终工作副本，Repair 评测其最后导出的补丁。
代码通过与流程完整结束分别计数；所有失败及实际消耗都留在分母内。

## 后续架构判断

先完成预算梯度实验，再根据高预算下重复出现的失败定位问题。重点检查规划输出无法解析、
角色在探索与交接中消耗预算，以及代码已通过固定验收却无法完成交付的情况。
如需优化，保留此轮基线，建立可复现回归用例，在新目录验证调整后的实现；不覆盖原始成绩。

## 本轮接口中断与恢复记录

首次执行期间，用户确认 DeepSeek 余额用尽，接口连续返回 HTTP 402。
中断恢复时保留 35 次不含接口故障的有效结果，将 147 次受 HTTP 402 影响的完整尝试、
4 次停止时尚未完成的尝试移入 `excluded-attempts/`，共 151 条。
这些尝试的原始事件、已返回 usage 和结果继续保留，但不计为模式失败，也不占用计划中的
288 个有效条件；受影响条件恢复接口后重新执行。

原始中断前总表保存在 `grid-before-provider-recovery.json`，恢复处理写入 `grid.json`
的 `provider_interruption` 和 `excluded_attempts`。原始实现仍保存在 `implementation.zip`。
评测器随后增加共享 HTTP 402 停止信号：任一客户端收到该错误后，停止派发新任务、阻止其他
客户端继续请求，并单独归档受影响尝试。该机制以脚本化模型验证，没有为验证停止机制消耗真实接口额度。

恢复只变更评测器的接口故障控制和记录，不变更产品源码、任务、Prompt、模型或预算。
使用 `--resume --resume-harness-update` 显式记录此次评测器修订，续跑会验证：除
`eval/run_budget_grid.py`、`eval/run_mode_comparison.py` 外的实现及所有条件必须一致。
新旧实现指纹和新实现归档路径保存在 `harness_revisions` 中。此标志不是放行产品架构变更的方式。

若再次出现 HTTP 402，进程结束时状态为 `provider_blocked`，不写完成时间；账户恢复后可以
使用相同条件续跑。`finished_at` 和完整的 288 条有效结果同时存在，才算本轮执行完成。

## 用户停止时的部分结果（2026-10-29）

用户要求停止实验，后台进程已结束。有效条件完成 210/288，`grid.json` 标记为
`stopped_by_user`，不写实验完成时间。本轮未补齐条件，以下仅作描述性结果，各单元格分母不同。
产品架构保持基线；只读角色结论输出的候选只在隔离副本通过回归，尚无真实模型对照，未应用到主仓库。

| 累计预算 | ReAct 额外测试通过 | Repair 额外测试通过 | ReAct 正常结束且通过 | Repair 正常结束且通过 | ReAct 平均 token | Repair 平均 token |
| --- | --- | --- | --- | --- | --- | --- |
| 60,000 | 19/19 | 14/17 | 18/19 | 10/17 | 38,248 | 57,513 |
| 120,000 | 18/18 | 17/17 | 18/18 | 16/17 | 39,286 | 72,636 |
| 240,000 | 17/17 | 20/20 | 17/17 | 20/20 | 48,061 | 62,587 |

重要反例：`60000/r3/line-tracking/repair` 被原始流程标为 verified，原始 9 项验收通过，
但额外测试 `test_line_and_escape_edges` 失败：混合换行输入的行号为 `[1, 2, 2]`，
期望 `[1, 2, 3]`。因此 fixed-test verified 不能解释为修复普遍正确；验证角色也未防止此反例。
它是本次预算梯度实验的新发现，不改变此前独立归档的初步实验结果。

目前证据支持将 Repair 定位为隔离执行、固定验收和补丁/证据交付流程；
尚未观察到其在这批局部任务上优于普通 ReAct 的修复率或 token 效率。
