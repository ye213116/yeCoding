## 事实基线与表述约定

1. 项目以既有终端 Coding Agent 为基础，论文重点是新增修复流程及其集成，不能把基础设施全部表述为本轮从零实现。
2. 通用 ReAct、Plan、Team 与 `repair` 是不同执行入口；容器隔离和固定验收适用于后者。
3. 修复流程采用顺序角色交接，只有一个写入者；不写成已实现多 Worker 并行修改与冲突合并。
4. Skill 是流程知识，Memory 是带来源的经验数据；当前没有证明二者带来独立准确率收益。
5. 修复任务为固定 python-dotenv 源码上的人工注入缺陷，不能称为真实历史 issue 或 SWE-bench 任务。
6. 核心对比为 8 个保留任务、3 种策略、24 次真实模型运行；2 个开发任务不计入该分母。
7. 单角色、评审反馈多角色、验证反馈多角色的流程验收成功数分别为 8、5、4；不得改写为多智能体提升成功率。
8. 自动化测试总数 160 包含既有回归，来源是归档执行记录。本批只读核验，不声称本批重新执行了全部测试。
9. 结果对应未提交工作区的实现指纹；Git HEAD 只是代码基线，不等于本轮全部实现所在的提交。
