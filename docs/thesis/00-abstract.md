# 摘要

编程智能体能够通过工具调用完成代码阅读、文件编辑和命令执行，但代码被修改并不意味着缺陷已经修复。面向仓库的自动修复还需要处理执行环境隔离、结果验收、失败反馈和资源预算等问题。多智能体协作可以分离任务规划、代码修改与独立检查，也会引入额外的上下文和协调开销。因此，需要将协作流程与实际执行证据结合，并明确其适用范围。

本文在既有 Python 终端编程智能体基础上，设计并实现了面向代码修复的多智能体协作与验证系统。系统保留通用工具调用能力，通过协调、修复和验证三个角色的独立上下文完成顺序交接；在任务工作副本中修改代码，使用受限 Docker 容器执行命令，并在新的验收副本中运行调用者预先指定的测试。系统根据执行结果组织反馈，在调用次数、token 阈值、尝试次数和总时限约束下继续修复或终止，保存候选补丁与运行报告。Skill 模块提供复现、最小修复和验证步骤；Memory 模块按项目作用域管理带验证来源、源码指纹和有效期的修复经验。

系统的验证记录显示，包含既有回归的 160 项自动化测试全部通过。实验基于固定版本 python-dotenv 源码构造了 10 个可复现的人工缺陷任务，其中 2 个用于开发、8 个用于保留评测。在相同预算设置下，单角色执行反馈、评审反馈多角色和验证反馈多角色三种策略的流程验收成功数分别为 8、5 和 4，共完成 24 次真实模型运行。各组均未观察到错误验收；多角色方案的失败均表现为预算耗尽，其中验证反馈方案有一次候选通过额外测试，但流程未在预算内完成。

功能测试验证了隔离执行、固定验收、受控重试和证据交付流程的可运行性，修复实验未显示多角色协作在该小规模任务集上的成功率优势。这些观察提示，对编程智能体的工程评估需要同时考察验收依据、协作成本和失败终止条件，不能仅依据模型自述或角色数量评价系统效果。

**关键词：**编程智能体；多智能体协作；验证反馈；容器隔离；经验记忆
