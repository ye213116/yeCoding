# 第1章 绪论

## 1.1 研究背景与意义

软件维护中的缺陷修复通常包含问题复现、代码定位、修改实现和回归验证等步骤。开发者需要在问题描述与仓库实现之间建立联系，检查被修改接口及其调用方，并通过运行结果判断修改是否满足预期。对于实际代码仓库，这些步骤既依赖代码生成能力，也依赖工具、执行环境和验证流程。只生成一段看似合理的代码，尚不足以完成可交付的修复任务。

大语言模型与外部工具结合，为上述过程提供了新的实现方式。ReAct 将任务推理与外部行动放入交替循环，使模型能够根据工具返回的信息调整后续操作。SWE-agent 进一步面向软件工程任务研究智能体与计算机环境之间的接口，涉及仓库导航、文件编辑和测试执行等活动。这些工作说明，编程智能体的行为受到模型能力和交互环境的共同影响。[@yao2023react; @yang2024sweagent]

当编程智能体获得文件写入和命令执行能力后，系统需要明确两个层次的结果：一是模型是否完成了修改动作，二是修改后的程序是否通过了约定的验收。前者可以通过工具调用是否成功判断，后者需要检查实际程序行为。模型输出中的“已修复”属于说明性文本，无法代替测试结果。同样，命令成功启动或正常退出，也不能自动证明任务要求得到满足。若系统没有区分这些状态，便可能将未验证的补丁作为成功结果交付。

多智能体协作提供了一种职责划分方式：协调角色负责组织步骤，修复角色负责修改实现，验证角色从独立上下文检查代码和证据。AutoGen 等工作提供了通过多智能体对话构建任务流程的框架，为角色分工与协作接口设计提供了参考。多角色划分也伴随额外的模型调用和上下文传递，其收益需要结合任务特点与资源预算评估，不能由角色数量直接推导。[@wu2024autogen]

此外，代码执行具有明确的工程边界。智能体生成的命令可能访问文件、启动子进程或改变运行状态，代码修改也可能干扰其他任务。为每个任务提供独立工作副本，能够隔离文件变更；在受限容器中执行命令，则可以限制执行范围与资源使用。工作副本和容器承担不同职责，系统需要同时考虑两者，并在超时、取消和异常退出后清理资源。

基于上述问题，本文将研究范围收敛到 Python 仓库的可执行缺陷修复。在保留终端编程智能体核心能力的前提下，重点实现角色协作、隔离执行、固定验收和反馈重试之间的衔接，形成能够输出补丁、验证依据与失败原因的完整流程。该工作的意义在于建立可检查的工程交付方式，并通过真实运行记录分析协作成本与适用边界。

## 1.2 相关研究与技术现状

### 1.2.1 工具驱动的编程智能体

ReAct 将推理过程与环境行动结合，使智能体能够利用外部反馈继续处理任务；SWE-agent 将软件工程智能体的行为落实到仓库导航、编辑与执行接口上。两者分别从行动循环和软件工程交互环境的角度，为编程智能体提供了基础思路。[@yao2023react; @yang2024sweagent]

本文复用已有 ReAct 工具循环承载代码读取、检索与修改，不重新训练基础模型。与单次生成代码片段相比，本系统关注仓库状态如何被改变、修改如何接受外部验收，以及失败后如何在约束条件内继续执行。系统的研究对象是执行流程及其工程实现，模型服务作为可配置的基础能力使用。

### 1.2.2 多智能体协作与反馈利用

AutoGen 通过可配置的多智能体对话组织任务执行，体现了角色之间通过消息和工具结果协作的实现方式。Reflexion 探索利用语言形式的反馈改进后续尝试，为任务反馈的保留与使用提供了另一种思路。两项工作分别从协作编排与反馈利用的角度，为系统设计提供参考。[@wu2024autogen; @shinn2023reflexion]

本文将角色分工落实为独立对话历史与工具权限：协调、验证角色执行只读检查，修复角色负责写入任务副本。反馈来源包括代码评审意见和执行器产生的测试结果。经验记忆保存可追溯的任务事实与验证来源，不对模型参数进行更新，也不将一次成功尝试直接推广为普遍有效的修复规则。

### 1.2.3 仓库上下文与代码检索

仓库级任务通常涉及多个文件及其关联信息。RepoCoder 通过迭代检索与生成利用仓库上下文，说明代码生成过程可以与外部代码信息的选择相结合，其迭代检索思路为仓库上下文组织提供了参考。[@zhang2023repocoder]

本文使用已有的 Python AST 解析、SQLite 符号索引和预算化上下文组装能力辅助代码定位。检索结果可以提供符号定义、可能的调用关系及源码片段，但静态关系只是一种近似，检索命中也不意味着模型已经理解或正确修改了代码。因此，代码上下文属于修复流程的输入支撑，最终仍需要执行测试验收。

### 1.2.4 基于执行结果的软件修复评测

SWE-bench 将真实仓库中的问题描述与代码修改任务相联系，并使用测试评估修复结果，为软件工程智能体提供了基于程序行为的评价方式。其数据来源和任务构造与本文不同，本文不将自建任务表述为 SWE-bench 实例，也不直接比较两者的成功率。[@jimenez2024swebench]

本文使用固定版本外部源码构造人工缺陷任务，先确认原始源码通过验收，再确认注入缺陷后测试失败。模型完成修复后，除流程中可见的固定验收外，还在独立目录加入额外测试，检查候选是否满足更多行为要求。该设计用于验证系统流程与分析失败原因；有限任务和测试覆盖无法证明候选在所有输入下正确。

现有工作分别提供了工具行动、角色协作、反馈利用、仓库检索与执行评测等思路。本文将这些问题落实到同一修复流程中，重点检查角色交接、执行边界、验收依据和资源终止条件是否一致，而不以提出新的基础模型或普遍优于既有系统的算法为目标。

## 1.3 问题定义与研究目标

### 1.3.1 任务定义

本文的修复任务输入由自然语言问题描述、固定的仓库初始状态、执行镜像、验收命令和资源预算组成。系统需要在任务副本中生成候选修改，并给出可追溯的执行结果。最终输出包括候选补丁、验收报告以及终止状态；系统不自动将补丁应用到用户原仓库。

本文将“候选通过测试”与“流程成功完成”作出区分。前者描述特定补丁在特定测试下的行为，后者还要求系统在约定预算内完成验收和交付。测试失败、环境错误、预算耗尽和取消等状态需要分别记录，不能统一归为成功或笼统的修复失败。初始源码已通过所有验收测试时，系统也不能据此声称完成了新的缺陷修复。

### 1.3.2 研究问题

围绕上述任务，本文关注以下三个问题。

第一，如何在保留通用编程工具能力的同时，为修复任务建立独立的文件变更和命令执行边界，使原仓库不被任务过程直接修改，并能够在超时或取消后清理执行资源。

第二，如何组织协调、修复与验证角色之间的交接，将候选补丁、实际测试结果和评审意见关联起来，并根据失败证据和剩余预算控制重试，避免仅以文字说明作为任务完成依据。

第三，在相同预算设置下，单角色执行反馈、评审反馈多角色和验证反馈多角色分别表现出怎样的验收完成情况、调用开销和失败类型。该问题允许出现多角色方案成本增加或完成率降低的结果，不预设多智能体具有优势。

### 1.3.3 研究范围

系统面向具有可运行验收测试的 Python 修复任务，执行环境由调用者预先准备。本文不涉及基础模型训练、任意语言的完整语义分析、并行补丁自动合并或虚拟机级安全隔离。Skill 和 Memory 作为系统组件进行功能验证，其独立质量收益不属于本轮对比实验已经证明的结论。

修复流程采用顺序角色交接，由单个修复角色写入工作副本。系统已有的通用 ReAct、Plan 和 Team 入口仍保留，但本论文讨论的容器约束和固定验收属于专门的修复路径，不能扩展表述为所有入口均已执行相同隔离策略。

## 1.4 本文主要工作

本文在既有终端编程智能体基础上完成以下工作。

（1）设计并实现独立的修复流程。复用模型客户端、工具调用循环和代码检索组件，组织协调、修复与验证角色，明确只读检查与文件修改的职责边界，并将同一流程接入命令行、交互式终端、SDK 和 Runtime 等入口。

（2）实现任务工作副本与容器执行机制。固定仓库初始状态，在副本中执行修改，检查候选对测试和关键配置的变更，通过受限容器运行命令与验收，导出可以与来源状态关联的补丁，避免直接覆盖用户原工作区。

（3）实现执行证据驱动的反馈与终止机制。保存基线测试、各轮补丁、执行输出和角色检查意见，依据实际结果组织重试；同时约束模型调用、token 阈值、尝试次数和总时限，对无进展、环境错误和预算耗尽等情况分别终止并保留记录。

（4）接入流程技能与项目经验记忆。使用三个内置 Skill 描述复现、最小修复与验证步骤，记录其版本及内容指纹；按原项目作用域召回经验，对自动保存的修复记忆附加验证来源、源码指纹和有效期，使其适用条件能够被检查。

（5）完成系统测试与受控对比实验。结合既有回归和新增测试验证功能，构造外部固定源码上的人工缺陷任务，比较三种反馈策略的流程验收结果、额外测试结果与调用开销，并保留预算失败，分析结论适用范围。

上述工作主要体现为系统设计、工程集成和证据组织。相关组件的可运行性与功能边界由测试和运行记录支持；多角色协作能否改善更复杂任务的修复质量，则需要新的独立任务与实验进一步研究。

## 1.5 论文组织结构

本文共分为七章。

第1章为绪论，介绍研究背景、相关工作、问题定义、研究范围和主要工作。

第2章介绍系统涉及的相关技术，包括工具驱动的智能体循环、多角色上下文、代码结构检索、Skill、Memory 和容器执行机制。

第3章进行需求分析，说明目标用户与修复场景，明确功能需求、资源约束、执行边界和验收条件。

第4章给出系统总体设计，包括分层架构、角色分工、任务与候选结果的数据组织、运行状态及公开接口。

第5章阐述核心功能实现，重点说明工作副本、沙箱执行、固定验收、反馈重试以及 Skill 和 Memory 的集成方式。

第6章介绍系统测试和实验设置，报告真实运行结果，区分验收完成、额外测试通过与预算失败，并讨论有效性限制。

第7章总结已完成的工作及其证据支持范围，分析系统局限，提出后续研究方向。
