# T1 文献综述与技术路线初稿

本课题把范围限定为 **Python 工程代码库的理解与上下文组织**。通信、DSP、嵌入式和 EDA
场景说明工程背景，但 T2 明确要求 Python 解析；当前成果不应写成已支持 Verilog/VHDL
的结构解析。以下是论文综述的工作稿，正式论文需按学校要求调整引用格式。

## 四个方向的相关工作

| 方向 | 代表工作与启发 | 本课题的取舍 |
| --- | --- | --- |
| LLM 编程智能体 | [ReAct](https://arxiv.org/abs/2210.03629) 将推理与外部行动交替进行；[SWE-agent](https://arxiv.org/abs/2405.15793) 研究文件编辑、仓库导航与测试接口对软件工程智能体的作用 | 采用已有 ReAct 工具循环承载原型，把研究重点放在检索和上下文，而非重新设计 Agent 架构 |
| 检索增强代码生成 | [RepoCoder](https://arxiv.org/abs/2303.12570) 通过检索与生成迭代利用仓库信息；[CodeRAG-Bench](https://arxiv.org/abs/2406.14497) 指出代码检索在词面重合不足时仍有难题 | 以关键词检索作为可复现基线，再比较结构索引；不把一次实验解释为通用代码生成能力提升 |
| 长上下文管理 | [Lost in the Middle](https://arxiv.org/abs/2307.03172) 发现相关信息在长上下文中的位置会影响模型表现 | 固定预算并优先放入关键符号和依赖；比较长度与回答质量，不假设“塞入更多代码”一定更好 |
| 代码结构分析 | [GraphCodeBERT](https://arxiv.org/abs/2009.08366) 展示代码结构信息对模型代码任务的价值，其方法涉及数据流预训练 | 本科规模采用标准库 AST 提取定义、import、可能的调用与继承关系；不训练新模型，也不把静态近似边当成精确运行时调用图 |

这些研究支持“仓库级上下文选择值得单独研究”的技术动机。它们研究的任务、数据集和
模型各不相同，论文不能直接拿其报告的分数与本系统分数做横向比较。本课题的实际贡献
应落在可复现的 Python 代码结构索引、固定预算打包策略及同任务三策略对比实验上。

## 技术路线

1. 用 `ast` 解析 Python 文件，形成文件、类、函数、方法、变量的符号记录和 import、调用、
   继承的可能关系；解析失败的文件仍可按文本检索。
2. 将符号、关系和文本行存入 SQLite 索引，按查询排序命中，并扩展必要依赖。
3. 在同一 token 预算内，依次组织符号签名、调用链、源码摘录和文件摘要，记录来源行号。
4. 把结构上下文交给现有编程智能体，支持代码问答、解释和小规模修改建议。
5. 使用同一任务集与同一模型，对比关键词摘录、直接输入文件、结构感知组装；报告
   上下文长度、符号召回率和生成有用性，保留逐任务数据与失败案例。

核心可检验假设是：在固定预算下，结构感知策略比两种基线更容易覆盖回答所需的
符号及依赖；生成有用性是否同时提升，必须以实际模型实验为准。
