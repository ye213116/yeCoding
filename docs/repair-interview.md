# 修复流程面试讲解

## 项目介绍

我在 Python 终端 Coding Agent 的基础上，实现了面向代码修复的验证反馈流程。
协调、修复和验证 Agent 使用独立上下文；修复发生在任务副本中，shell 在禁网容器执行。
系统提取候选补丁，在新的只读副本中运行固定验收测试，再将失败证据反馈给修复 Agent。
最后交付补丁、测试报告、调用量和失败原因，原仓库不被自动修改。
Skill 负责复现、最小修改和验证流程，Memory 负责携带来源与适用版本的历史经验。

## 可以展开的设计决策

| 问题 | 实际实现与取舍 |
| --- | --- |
| 为什么多 Agent？ | 将修改与检查放在独立上下文中；需要通过实验检验收益，不能预设比单 Agent 更好 |
| 如何避免并发写冲突？ | 当前只有一个修复写入者，角色顺序交接，先确保结果和证据可追溯 |
| 谁决定成功？ | 执行器产生的固定测试结果；模型的通过意见不能覆盖失败退出码 |
| 测试如何固定？ | 调用者指定命令；测试与关键配置的改动在工具层和补丁导出阶段被拒绝 |
| 沙箱与工作副本分别做什么？ | 副本隔离修改，容器约束执行；两者都需要，目录隔离本身不能限制 shell |
| 怎么避免无效重试？ | 最大尝试数、全局模型调用数、usage 阈值、总超时、空补丁和重复补丁停止 |
| Skill 与 Memory 有何不同？ | Skill 保存操作步骤；Memory 保存具体任务经验与验证来源 |
| 如何避免记忆串线或过期？ | 使用原项目作用域；修复经验召回要求源快照指纹一致，并设置过期时间 |
| 如何处理取消？ | 取消异步执行时清理命名容器；Runtime 队列保留既有取消后拒绝迟到结果的语义 |
| 验证有什么边界？ | 测试只能覆盖指定行为；评测额外使用 Agent 不可见的测试，仍不能证明普遍正确 |

## 现场演示顺序

1. 准备 `eval/prepare_repair_demo.py` 的开发案例，展示修改前测试失败。
2. 从 `yecoding repair` 执行修复，解释三个角色和固定验收。
3. 打开报告与候选补丁，核对失败基线、修改文件、测试结果和 usage。
4. 展示原项目未被修改，以及预算耗尽/无进展等失败终止记录。
5. 展示对比实验的真实成功数和成本，同时说明任务来自人工注入缺陷。

## 面试中需要保持准确的说法

- 这是基于固定版本外部源码的受控实验，不能称为修复真实上游历史 issue。
- 多 Agent 的准确率收益必须由结果支持；成本增加和预算耗尽同样需要展示。
- `verified` 表示候选通过固定验收，补丁尚未自动应用。
- 容器隔离适用于 `repair` 路径；普通 Agent 路径仍使用既有审批与守卫。
- Python AST 调用关系是近似静态分析，动态分派不能保证完整解析。

具体使用方式见 [修复流程](repair-workflow.md)，原始实验在 `eval/evidence/repair-*.json`。
