## 本次结果（2026-10-29）

正式实验已完成：北京时间 15:47—16:01，`deepseek-v4-flash`，8 个保留任务 × 4 种模式，
共 32 次真实运行、275 次模型请求、1,600,430 个累计 token。另有 4 次开发任务试跑，不计入表内。

| 模式 | 固定验收通过 | 额外测试通过 | 正常结束且额外通过 | 平均 token | 平均主体耗时/秒 |
| --- | --- | --- | --- | --- | --- |
| 普通 ReAct | 8/8 | 8/8（100%） | 8/8 | 37,374 | 13.39 |
| 普通 Plan | 3/8 | 3/8（37.5%） | 0/8 | 41,831 | 25.78 |
| 普通 Team | 0/8 | 0/8（0%） | 0/8 | 64,597 | 35.48 |
| Repair / verified | 6/8 | 6/8（75%） | 3/8 | 56,251 | 20.92 |

本轮在指定工具环境和预算下，ReAct 的完成率最高，平均 token 最低；没有观察到 Repair 优于
普通 ReAct。Repair 有 3 个通过额外测试的候选在验证角色阶段耗尽预算，因此代码通过数为 6，
完整流程成功数为 3。另两次 Repair 在导出候选前耗尽预算，未取得可供外部测试的补丁。
这显示了固定验收已经通过后继续执行验证角色的成本，不证明验证角色在其他任务上没有价值。

Plan 的 5 次预算失败中有 3 次留下通过额外测试的代码。其余 3 次为规划 JSON 解析错误，
原始模型事件均记录 `stop_reason=max_tokens`：单次 2,048 token 输出额度（包括 reasoning）
导致输出截断或没有可解析的 JSON。因此表中成绩是该预算条件下的入口可用性结果，不能据此
断言 Plan 的修复算法不如其他模式；本轮没有复跑默认 8,192 输出额度这一条件。

Team 的 8 次运行均耗尽预算且没有通过外部测试。调用记录可见，部分任务在仓库探索、

所有 Repair 运行仅建立一轮尝试记录，本轮仍没有建立多轮反馈提高修复率的证据。

## 实验问题与口径

本实验比较公开 SDK 的 `QueryEngine.ask`（ReAct）、`QueryEngine.plan`、
`QueryEngine.team`（默认 ReAct worker）与 `QueryEngine.repair`（`verified` 策略），
检查它们在同一批缺陷、相同模型和预算下交付的代码能否通过外部测试。

这是**统一工具环境下的真实编排入口对照**：普通模式使用已有的 Agent、PlanExecuteAgent、
AgentOrchestrator，评测器为其注入与 Repair 相同的读取、检索、编辑和 Docker 命令工具。
文件守卫、固定测试保护、禁网容器也一致。因此它没有比较普通 CLI 默认宿主命令、完整工具集、
交互审批及外部 MCP 的端到端使用体验。没有把 Repair 内部的 `single/team` 消融冒充普通模式。

四组使用同一段任务文字，明确要求实际编辑、说明验收命令与容器环境。Repair 保留自身的
自动基线、角色 Skill 注入、候选检查和固定验收流程；普通模式保留自身的规划、工具调用、
评审及结束逻辑。这些模式差异是比较对象，不额外给普通模式增加修复重试编排。

## 可复现运行

```bash
# 需要有效模型配置、Docker，以及本地已有的 python:3.11-slim 镜像。
# 输出路径必须不存在，避免覆盖历史证据。
uv run python -m eval.run_mode_comparison --split dev --limit 1 --output-tokens 2048 \
  --out eval/results/mode-pilot.json
uv run python -m eval.run_mode_comparison --split heldout --output-tokens 2048 \
  --calls 18 --tokens 60000 --timeout 300 \
  --out eval/results/mode-heldout.json
```

脚本加载 `--config-root`（默认仓库根目录）的模型配置。固定 temperature=0、单次最大输出
2048 token；关闭 Memory、MCP 和自定义 Prompt 文件，保留配置中的 Skill、上下文压缩和
代码索引开关。记录模型名称和供应商，不保存密钥及完整连接配置。

执行中的模型命令只在独立 Docker 副本内运行；验收以只读方式挂载另一个干净副本。
普通模式的文件工具复用 Repair 的保护逻辑，所有模型命令都复用 DockerSandbox。
不进行人工审批等待，授权范围仅为这些副本内的工具。原始任务源码在每组后校验指纹。

8 个保留任务取自固定 python-dotenv v1.1.1 源码上的人工注入缺陷；开发任务试跑不计入正式结果。
每个任务每种模式运行一次，共 32 次。任务间轮换四种模式的执行顺序；各次运行顺序执行。
每次新建模型客户端、上下文、工作副本和预算计数器，不复用上次修复结果。

每次最多 18 次模型请求、累计 60,000 token、300 秒；Repair 最多 3 轮尝试。
累计 token 根据模型返回 usage 在下次请求前检查，不是严格的计费硬上限，最后一条请求或
并发中的请求可能越过阈值。Plan/Team 的多个内部角色共享同一个预算客户端；角色内部捕获
预算异常也会被外层记录为预算耗尽。模型请求次数统计在共享客户端边界，不累加入口的重复事件。

## 外部判定

- **固定验收通过**：最终可取得的代码在评测器控制的原始 9 项验收上全部通过。
- **额外测试通过**：再加入模型运行期间不可见的 4 项测试，全部 13 项通过。
- **正常结束且额外通过**：普通模式发出 done 且没有被观察到的错误或预算拒绝，或 Repair
  返回 verified，同时额外测试通过。普通模式的 done 本身不保证内部每个任务都成功。
- **预算耗尽 / 解析错误 / 超时**：保留失败运行及其成本，不从分母剔除。

普通模式评测最终工作副本，即使流程中断也尝试导出补丁；Repair 评测其最后导出的候选或
尝试补丁。Repair 在生成补丁前中断时可能已有临时编辑，但临时目录已由正常实现清理，
此时记为无可评测候选，不推断代码正确与否。无补丁、无效补丁、修改固定测试的候选不会记为通过。

额外测试只在模型运行结束后放入评测目录。测试内容由评测器写入，模型编辑后的测试不能替代
原始验收。模型说“已修好”不参与通过判定。没有导出候选的运行仍保留在总分母中。

平均 token、请求次数和主体耗时包含失败运行。主体耗时不包含评测器追加的外部测试；
普通模式包含编排与模型工具调用，Repair 还包含其内建基线与验收。因此耗时比较反映各路径的
整体工作量，不能直接解释为模型推理速度。机器非独占、缓存和供应商负载也影响耗时。

## 证据位置

本次原始证据位于 `eval/evidence/mode-comparison-20261029/`：

- `pilot.json`：1 个开发任务 × 4 种模式。
- `heldout.json`：8 个保留任务 × 4 种模式及汇总。
- `*-runs/`：逐次结果、最终补丁、模型事件和容器命令记录；Repair 原始报告另存于 repair 子目录。

报告包含开始/结束时间、Git HEAD、实际 Python 实现文件及 fixture 哈希、Docker 镜像 ID、
任务源码指纹、验收测试哈希和完整外部测试结果。哈希覆盖未提交的评测脚本，因此不能仅用 HEAD
代表这次实验实现。既有 `repair-heldout-live.json` 保留不变，不与本次结果合并统计。

本实验是单项目、8 个局部人工缺陷、每条件一次运行的探索性对照。不能据此推断真实复杂缺陷的
普遍成功率、显著性或多轮反馈收益。普通模式若在规划解析阶段失败，反映当前模型与入口组合
的可用性问题，也不能直接当作修复算法能力差异。
