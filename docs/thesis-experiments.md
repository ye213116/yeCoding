## 实验设置

两个任务集分别为本项目 10 个自建任务与 python-dotenv v1.1.1 的 12 个独立任务，
不合并统计。独立仓库使用固定 commit 的 8 个 Python 生产文件，排除上游测试。
查询及真值先按源码标注，再运行检索；运行后未为提高结果而更改算法或任务。
三种主策略为关键词摘录、直接文件前缀和结构感知；第四种仅关闭结构方法的依赖扩展。
检索预算为 2000 和 4000，统一使用近似 token 估算。

独立集在 4000 预算下使用配置模型 `deepseek-v4-flash` 完成 48 次回答与 48 次评分调用，
生成/评分温度均为 0、思考模式关闭、各调用输出上限 1024。评委只得到问题、
真值符号/文件名称和回答，未获得参考事实或完整源码；这一点直接影响评分可信度。

以下为任务均值±样本标准差。有用性中的 n 是实际评分数；源码覆盖是
符号定义区间行覆盖的任务内平均，详情见 `eval/README.md`。

## 可以支持的观察

- 独立集 2000 预算下，结构方法核心符号召回为 100%，两种基线均为 79.17%；
  4000 预算下，四种方法均为 100%。收益依赖预算，不能写成所有设置下都改善核心召回。
- 独立集完整方法的核心及依赖召回为 88.33%，关闭依赖扩展后为 64.44%，差 23.89 个百分点。
  两者平均上下文长度分别为 1243 与 926。这支持该任务集上的依赖覆盖收益。
- 独立集 4000 预算下，结构方法比直接文件上下文短约 65.6%，比关键词摘录短约 19.8%。
  这描述的是返回代码长度，未计索引构建成本，也不是供应商实际输入账单 token。
- 直接文件的定义区间行覆盖为 85.42%，结构方法为 56.00%。更多相关接口覆盖没有转化为
  更完整的函数体覆盖，需要同时报告这两个维度。
- 完整结构方法、关闭依赖扩展、直接文件的模型评分均值均为 4.75；关键词为 4.58。
  完整与消融策略的逐任务评分全部相同，本轮没有观察到依赖扩展提升该评分。
  不报告“显著提升”或普遍生成质量改善。

## 失败案例与评分争议

以下是 Agent 辅助的源码核对，不冒充人工评测。`eval/evidence/source-checks.json`
包含 D05/D06 的实际源码调用验证。

| 案例 | 实际行为及输出问题 | 可复核的原因 |
| --- | --- | --- |
| D05，override 优先级 | grep 回答错称 override=False 不使用系统环境；直接文件回答正确解释两分支，却被评委打 2 分 | 评委只有符号名称而没有语义参考事实，分数不能作为正确性的唯一依据 |
| D06，无等号与空值 | 实际 KEY 的值为 None、KEY= 的值为空字符串；结构及消融回答都说两者是空字符串，仍被评委打 4 分 | 源码候选前 3 项被文件符号、IPython dotenv 方法与 DotEnv 类占据；真正的 parse_binding/parse_value 只有签名 |
| D08，错误位置 | 结构回答否认错误原文含行号或遗漏保留方式 | 关键 get_marked 与异常恢复实现未完整呈现，签名覆盖不足以解释状态变化 |

D06 的上下文只包含两个源码块，却具有 100% 核心符号召回，并未耗尽 4000 预算。
这表明源码候选选择规则存在独立于 token 预算的失败模式。下一轮应按通用规则改进源码
候选选择，并用新的冻结测试任务验证，不能针对这些标签硬编码排序或用同一批任务反复调参。

## 有效性限制与下一轮实验

两个仓库样本仍少，自建集同源偏差较大；独立任务由源码阅读者标注，未经过独立专家确认。
固定检索词含已知接口名称，不能代表完全未知命名的问题。file 是关键词选文件后取前缀，
grep 是确定性模拟，没有真实 Agent 多轮导航。这一轮测的是上下文提供策略，不是完整
端到端修复成功率。工具次数是模拟值，不用于计算真实网络开销。

模型兼任生成器和评委，评分存在天花板和错判，温度 0 也不等于绝对可重复。
正式论文先让学生/导师填写隐藏策略的 `review.csv`，结合参考事实与源码核查，
再报告人工正确性、完整性和有用性。原始模型评分保留，不按人工判断改写旧报告。

下一轮优先事项：改进宽泛符号挤占源码位置的规则；增加未知接口名称或跨文件推理任务；
比较改进前后检索及人工回答质量。如果要宣称 bug 定位或代码修改效果，再加入可执行测试
判定的任务。当前已有结果足以撰写方法、实验设置、检索结果和失败分析工作稿。
# 验证反馈修复实验补充（2026-10-20）

本节是独立于代码上下文检索实验的新增实验。原始记录：
`eval/evidence/repair-fixtures-validated.json`、`repair-dev-live.json`、
`repair-heldout-live.json`、`repair-cli-demo.json`；实现与镜像指纹见 `repair-implementation.json`。

任务基于固定 python-dotenv v1.1.1 源码，人工注入缺陷，2 个开发任务、8 个保留评测任务。
全部 10 个任务均已在真实 Docker 中确认：未修改上游源码通过，注入缺陷后验收失败。
测试为本项目编写；这些任务不是历史 issue 或 SWE-bench。模型为配置的 `deepseek-v4-flash`，
温度为 0，每组最多 18 次调用、60,000 token 阈值、3 次修复、180 秒。
token 阈值在下一次调用前检查，因此最后一次返回可以超过阈值。

三组均执行固定验收。`single` 使用一个修复角色和执行反馈；`team` 使用协调/修复/验证角色，
后续反馈仅为不接收新测试结果的代码评审意见；`verified` 同时使用评审和测试证据。
这是新修复流程的受控反馈消融，不是原有通用 Team 与新流程的直接比较。
各运行独立，关闭跨任务 Memory；Skill 开启。额外测试在模型结束后加入独立目录，
Agent 不可见，也不使用其反馈重试。

| 方案 | 流程验收成功 | 额外测试通过 | 错误验收数 | 平均 tokens | 平均耗时（秒） |
| --- | --- | --- | --- | --- | --- |
| single | 8/8 | 8/8 | 0 | 31,120 | 13.44 |
| team | 5/8 | 5/8 | 0 | 64,541 | 17.00 |
| verified | 4/8 | 5/8 | 0 | 60,167 | 18.06 |

包含失败运行的 token 和耗时一起统计。两种多角色方案共 7 次预算耗尽；
`verified` 有一次最后的候选通过额外测试，但流程未在预算内完成，仍记作预算失败。
三组均有固定测试把关，错误验收为 0 不能归因于增加了验证 Agent。

这轮结果不支持多 Agent 提高修复成功率：任务简单，协调与复查的上下文成本明显增加，
统一预算下单 Agent 表现更好。它支持的是执行证据、预算终止和补丁交付机制已经能真实运行。
当前不根据保留任务结果修改模型预算后重报成绩。

有效性限制：每个任务每组仅运行一次；人工缺陷多为局部修改；额外测试仍是有限覆盖；
本次耗时记录期间同机有回归测试负载，不能作为严格性能比较；
未独立评估 Skill 增益，也未完成跨任务 Memory 增益实验。
后续要研究协作收益，应先冻结更复杂、跨文件的独立任务集，并报告重复运行分布。
